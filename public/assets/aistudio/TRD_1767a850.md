**Purpose:** defines *how* the system is built: stack, architecture, code standards, security, performance, integrations, environments, testing and release. The AI agent must follow this file for every technical decision. Data fields live in `Schema.md`; behaviour in `PRD.md` / `App-Flow.md`; visuals in `UI-Spec.md`.

## 2. Architecture

### 2.1 System diagram
```
┌────────────── Flutter App (Android + Web) ──────────────┐
│ Presentation (screens/widgets)                          │
│   └─ Controllers (Riverpod Notifiers)                   │
│        └─ Repositories (interfaces)                     │
│             └─ Data sources (Firestore / Functions SDK) │
└───────────────┬──────────────────────────────┬──────────┘
                │ reads, simple writes          │ callable (privileged actions)
                ▼                               ▼
        Cloud Firestore  ◄──────────  Cloud Functions (TypeScript)
        Cloud Storage                 ├ ingestPunches (HTTPS)
        Firebase Auth (claims)        ├ processDay / reprocessRange
        FCM                           ├ submitLeave / decideLeave / cancelLeave
                                      ├ decideAdjustment / decideOT / manualAttendance
                                      ├ lockMonth / reopenMonth / exportReport
                                      └ schedulers: nightlyClose, reminders, yearRollover

ZKTeco devices → Head Office server → Bridge service → HTTPS + API key → ingestPunches
```

### 2.2 Golden rules
1. **Clients never write privileged data directly.** Attendance results, leave decisions, balances, month locks, audit logs and role claims are written **only by Cloud Functions**.
2. **Rules + UI both enforce permissions.** Hiding a button is not security.
3. **Idempotent writes.** Punch IDs and day records use deterministic IDs (`empId_yyyyMMdd`, hash of device+time).
4. **Denormalize for reads, normalize for truth.** Display fields copied into transaction docs; masters stay the source.
5. **Pre-aggregate dashboards** (`dailySummary/{date}`) so KPI screens read 1 doc.
6. **All time logic in `Asia/Dhaka`**, stored as UTC `Timestamp` plus `dateKey` string.
7. **Every override and approval is audited.**

```

```
Features: auth, dashboard, employees, org, shifts, attendance, leave, overtime, reports, notifications, settings, audit.

### 2.4 Code standards
- `flutter_lints` + `very_good_analysis` style; zero analyzer warnings.
- Files < 300 lines; widgets small and `const` where possible.
- No Firestore/Functions calls inside widgets; use repositories.
- Business rules (late, leave balance, OT rounding, roster resolution) are **pure Dart/TS functions with unit tests**; the same rule is implemented once server-side (authoritative) and once client-side only for instant validation.
- Naming: `snake_case` files, `PascalCase` classes, Firestore fields `camelCase` (match Schema.md exactly).
- Errors: typed failures (`AppFailure`), user-friendly bilingual messages, details to Crashlytics.
- No hard-coded colours/strings (use theme tokens and ARB keys).
- Secrets never in repo (`key.properties`, `*.jks`, service accounts git-ignored).

## 6. Attendance device integration (ZKTeco)

**Flow:** device → Head Office server (existing store) → **bridge** → Cloud.

Bridge requirements:
1. Runs as a Windows Service or scheduled task on the Head Office server; Python (`pyzk`) or Node.
2. Reads punches since a persisted checkpoint (SQLite file); normalizes to `{deviceId, deviceCode, punchAt ISO +06:00}`.
3. Sends batches (100–500) to `POST /ingestPunches` with `x-api-key`; retries with exponential backoff; persists unsent queue locally.
4. Idempotency: server derives punchId = SHA-1(`deviceId|deviceCode|punchAt`); duplicates ignored.
5. Heartbeat every 5 minutes updates `devices/{id}.lastSyncAt`; alert if stale > 15 min.
6. Needs only **outbound HTTPS (443)** from the server. No inbound ports.
7. Employee mapping: `employees.deviceCode` ↔ device user ID; unmapped codes land in an "Unmapped punches" admin list.
8. Time sync: devices and server on NTP; function rejects punches > 1 day in the future.

## 7. Cloud Functions requirements
- TypeScript, Firebase Functions v2, Node 20, strict mode.
- Every callable: auth check → role/scope check → input validation (zod) → transaction/batch → audit → notification.
- Use Firestore **transactions** for leave balance changes.
- Schedulers use timezone `Asia/Dhaka`: `nightlyClose` 00:30, `reminders` 10:30, `yearRollover` Jan 1 01:00, `backup` 02:00.
- Idempotent triggers (guard with `processedAt`/version fields) to survive retries.
- Structured logging (`logger.info/error`) with `empId`, `dateKey`, `requestId`.
- Error codes mapped to client-friendly messages (`failed-precondition`, `permission-denied`, `already-exists`).
- Unit tests with the emulator for: late calculation (incl. night shift), leave approval chain, balance deduction, month lock, OT rounding.

## 15. Workforce Map and Luxury Motion — technical requirements

### 15.1 Map geometry
- Source: an **open administrative boundary dataset** for Bangladesh level-2 (64 districts). Candidates: geoBoundaries (ADM2), OCHA/HDX COD-AB Bangladesh, OpenStreetMap extracts. **Check the licence of the dataset you choose** (e.g., CC BY 4.0 / ODbL need attribution; avoid datasets restricted to non-commercial use) and show attribution in Settings › About.
- Processing (one-time, in `tools/geo/`): download → simplify with **mapshaper** (`-simplify 8% keep-shapes`) → target **≤ 300 KB** → normalise names to our ids (`districts.json`) → compute label points (`polylabel`) → export `assets/geo/bd_districts.json`. Add a unit test: exactly 64 features, ids match `districts.json`, no duplicates.
- Do **not** copy any third-party infographic artwork; only the *style* is reused.

### 15.2 Rendering in Flutter
- Convert each GeoJSON polygon to a Flutter `Path` once at startup (equirectangular or simple Mercator projection fitted to the canvas); cache paths in a provider.
- Draw with `CustomPainter` inside `InteractiveViewer` (min 1×, max 6×); one `RepaintBoundary` for the map, a second for the label layer.
- Fill with a single `ui.Gradient.linear` shader over the country bounds (`gRed`), opacity per district = share/maxShare (min 0.35).
- Hit-testing: transform the tap with `TransformationController.toScene`, then `path.contains(point)`; for tiny districts pick the nearest centroid within 12 dp.
- Labels: draw with `TextPainter` (halo via a second stroke paint); collision control = greedy placement by descending share; zoom-based visibility (see UI-Spec §17.2).
- Performance: pre-build `ui.Picture` for the neutral base map; only repaint highlighted districts when data or animation value changes. Target 60 fps on a 2 GB device; map first paint < 500 ms after data arrives.
- Poster export: `RepaintBoundary.toImage(pixelRatio: 3)` → PNG; PDF via `pdf` package.

### 15.3 Data pipeline (real-time)
1. Employee write → Cloud Function **`onEmployeeGeoWrite`** (idempotent; uses `event.id` guard) computes deltas and updates `geoStats/*` and `geoStatsPublic/*` with `FieldValue.increment` in one batch.
2. Client subscribes to a **single document** per scope (`geoStats/all`, `geoStats/dept_x`, …) → real-time updates cost 1 read per change, not 1,200.
3. Nightly **`rebuildGeoStats`** recounts from `employees` and repairs drift; admin callable to run on demand; alert if drift > 0.
4. Sanitization (`count < 5 → others`) is done server-side so the client never receives small-group details.
5. Bulk import of employees: function receives many writes → use batched increments; consider a debounce (`rebuildGeoStats` after import completes).

### 15.4 Testing
Unit: delta calculation for create / update district / status change / dept change / delete; sanitization threshold; percent maths (excludes "not set"). Emulator: change Cumilla → Habiganj and assert both docs. Widget/golden: map painter with fixture data (3 districts highlighted). Rules: non-HR cannot read `geoStats`, can read `geoStatsPublic`.

### 15.5 Luxury motion — implementation rules
- Central `MotionPrefs` provider: `liteMode` (auto + manual), `reduceMotion` (OS), `batterySaver`. All animated widgets read it.
- Aurora = one `CustomPainter` + one `AnimationController` per screen; paused with `TickerMode`/visibility; static when lite.
- Use `TweenAnimationBuilder`/implicit animations for count-up, fills and progress; avoid per-frame `setState`.
- Avoid `BackdropFilter` in scrolling lists; max 2 blur layers visible.
- Frame monitoring: `SchedulerBinding.addTimingsCallback` → if 90th-percentile frame > 20 ms for 3 s → switch to lite and log a Crashlytics non-fatal `motion_downgrade` with device model.
- Test on at least one low-end Android (2 GB RAM) before each release; add a performance trace `workforce_map_first_paint`.
- Letter-spacing is applied only to English overlines (never Bangla).

## 16. Analytics Dashboards — technical requirements

### 16.1 Data strategy
- Dashboards read **pre-aggregated** docs only (`dailySummary`, `monthlySummary`, `leaveIndicators`, `performanceSummary`; see Schema §11). Typical dashboard = 5–15 document reads; never scan `attendance` for charts.
- Ranges: 7D/30D → `dailySummary` (7–30 docs); 3M/12M → `monthlySummary` (3–12 docs per scope). Heatmaps use the `heatmap` map inside `monthlySummary`.
- Top-10 lists (late/absent) come from a small `monthlySummary.topLate/topAbsent` array or a callable `topEmployees` with limit 10.
- Real-time: listen only to "today" docs; historical data fetched once and cached (Riverpod `keepAlive`, 5-minute TTL).
- Consistency: the same TypeScript formula module is used by `rebuildMonthlySummary` and the report exports; tests assert dashboard = report.

### 16.2 Charts
- `fl_chart` for wave, bar, radar; **custom `CustomPainter`s** for donut, gauge, heatmap, ring cluster (full gradient + animation control). Pin the `fl_chart` version and check that gradient properties you use are supported in that version; fall back to custom painters if not.
- Central `ChartTheme` (colours from UI-Spec §18.2) and `MotionPrefs` (Lite mode) injected via Riverpod.
- Entrance animation triggered once when the chart first becomes visible (`VisibilityDetector` or sliver position); state kept so it does not replay on scroll.
- Series limited to ≤ 60 points (server pre-bins or client downsampling with LTTB); labels rounded for readability.
- Tooltips/crosshair use `RepaintBoundary` overlays to avoid repainting the whole chart.
- Poster/PNG export with `RepaintBoundary.toImage(pixelRatio: 3)`; PDF with the `pdf` package.

### 16.3 Performance budget
| Item | Target |
|---|---|
| Dashboard first paint (cached) | < 800 ms; fresh < 2 s on 4G |
| Chart frame time | < 16 ms on mid-range Android; auto-switch to Lite mode if p90 > 20 ms for 3 s |
| Charts animating simultaneously | ≤ 4 |
| Memory (dashboard) | < 150 MB on 2 GB device |
| Reads per dashboard open | ≤ 20 |

### 16.4 Security and privacy
- Leave Indicator flags and performance data are **HR-restricted** (rules in Schema §11.5); client never receives other employees' flags.
- Pattern flags are review prompts; wording in UI must stay neutral; audit who viewed/marked reviewed.
- Performance appraisals visible to the employee only after `status = published`.
- Exports containing individual data are role-checked and logged in `auditLogs`.

### 16.5 Testing
- Unit: metric formulas (attendance rate, punctuality, absenteeism, leave utilization, ADS, weighted appraisal score); leave-indicator rules (thresholds, 90-day windows, adjacent-off pattern).
- Function emulator tests: `rebuildMonthlySummary`, `computeLeaveIndicators`, `buildPerformanceSummary` with fixture data.
- Golden tests for each chart widget with fixed data and `animationsEnabled = false`.
- Integration: approve leave → donut and gauge update; dashboard number = monthly report number.
- Manual: low-end device test for Lite mode and animation smoothness.
